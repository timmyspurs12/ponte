# Phase 2B.3.2A — Bounded calldata and ABI preflight

This local-only synthetic evaluator is not an executable quote, deployment or activation. The optimizer core is unchanged. This document describes the implementation; successful compilation or TestVM tests do not establish network readiness or WASM runtime behavior.

## Entrypoint and limits

`#[storage]` and `#[public]` retain the SDK 0.10.10-generated storage accessor, non-payable check, selector, and typed `Router`. The struct no longer uses `#[entrypoint]`; it has a manually implemented `stylus_sdk::stylus_core::storage::TopLevelStorage` marker. It is the invocation's root storage, with no storage fields and no external calls. The custom `user_entrypoint` is WASM-only and excluded for the `stylus-test` and `contract-client-gen` features. It constructs the SDK `VM`/`WasmVM`, rejects reentrancy, references `pay_for_memory_grow(0)`, then uses `dispatch_bounded`. That function refuses over-cap `len` before the host reader is called; otherwise it reads once and preflights the same bytes that are handed to SDK `router_entrypoint`. Both normal and early bounded failures go through `flush_cache(false)` and `write_result`; SDK success is status 0, revert status 1. Reentrancy retains the SDK's immediate status-1 return.

The **25,572-byte** cap includes the 4-byte selector and is the maximum *canonical encoded length* for 64 candidates with four 64-byte asset strings: 4 selector + 32 top-level offset + 352 request head + 576 asset tuples + 24,608 array length and 64 twelve-word static candidates. It is not a measurement of gas, ink, memory use, execution cost or deployability. It was independently checked using ethers.js 6.16.0 `Interface.encodeFunctionData` for the original tuple: selector `0x31631981`, encoded length **25,572 bytes**. Ethers was installed in a temporary directory only, not added as a project dependency. A Rust test independently asserts the same maximum with Alloy's encoder. Even a canonical 65-candidate request with four empty strings is 25,700 bytes; a shorter, complete 65-candidate noncanonical input with aliased asset tuples is used to test the count gate below the cap.

## Preflight policy

For the known selector, the no-allocation parser uses checked slices, `usize` word conversion and checked arithmetic to examine the request and asset heads, their dynamic offsets, all four string lengths and padded data spans, the candidate-array length and its static-element body. Dynamic offsets must be word-aligned and beyond their containing tuple's head. It permits counts 0–64 and strings 0–64 **UTF-8 bytes**; a 65th candidate or 65th byte reverts before the typed router. Count 0 and other in-budget domain errors continue to be handled by the existing core. Alloy still validates scalar words and UTF-8, and the core still enforces its printable ASCII and other domain rules.

This is a bounds-and-alignment preflight, **not full canonical ABI validation**. It requires padded string spans, unlike inputs the pinned decoder may accept if padding is truncated. It does not require padding bytes to be zero, nor forbid trailing bytes or aliases/overlaps if all checked spans are safe; the total cap still applies. Unknown, missing and short selectors pass to the SDK router for its normal failure handling when within the cap. Canonical requests within the cap retain their selector and encoded result format. Over-limit requests now revert with empty data rather than returning an encoded `SyntheticResult` domain error; their validation-error precedence can therefore differ.

## Evidence and limitations

Native tests exercise the same bounded orchestration with reader/router spies and with SDK TestVM plus the actual generated router, including 0/1/64/65 candidates, max-length calldata, multibyte UTF-8, large/invalid offsets, truncation, unknown selectors and non-payable behavior. The existing fixture test additionally routes all 49 ABI-representable fixtures through the boundary: accepted cases retain their results, while the 65-candidate fixture has the documented boundary revert. Existing direct core/router checks remain intact.

GitHub Actions provides the authoritative status of formatting, native tests, Clippy, SDK ABI comparison, locked WASM compilation and narrow import/export inspection; consult the PR checks for their actual outcome. TestVM and the injected reader do **not** execute compiled WASM, establish allocation high-water marks, measure gas, or simulate a chain. No independent Solidity client ABI is produced here; that remains a separate milestone. Full WASM execution, broader adversarial testing and independent review remain outstanding. No `cargo stylus check`, RPC, wallet, deployment, activation or transaction is part of this milestone.
