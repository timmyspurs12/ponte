## 2. What the merged optimizer already provides

**Observed in repository:** `rust/optimizer` is an independent Rust 2021 `no_std + alloc` library, with `#![forbid(unsafe_code)]` in our crate, Rust 1.91.0, a committed Cargo.lock, and `alloy-primitives = =1.5.7` with default features disabled. `model.rs`, `arithmetic.rs`, and `optimizer.rs` supply typed requests, checked U256 arithmetic, deterministic validation and selection; `json.rs` is an offline wire codec. `src/bin/optimizer-v1.rs` is a host JSON-lines test/benchmark adapter, not a contract or production API. No Stylus SDK, ABI entrypoint, or `Stylus.toml` is present in this crate. The [Phase 2B.1 report](PHASE2B_IMPLEMENTATION.md) records native and WASM **library** builds and 10,760 finite differential comparisons with zero mismatches; this does not prove Stylus activation, runtime behavior, gas cost, or production correctness.

The core handles 1–64 candidate routes, `u128` amounts/rates/liquidity/costs, `u16` bounded bps, `u64` timestamps, and bytes32 route and snapshot IDs. It validates structural constraints, checks candidate expiry, capacity and liquidity, uses checked multiplication/division, ranks by output/cost/route ID and returns ordered rejection reasons or `NO_ROUTE`. Its supplied timestamps, IDs, prices and liquidity are **not authenticated**; synthetic metadata and caller-supplied time are not onchain market data or anti-replay protection. It does not discover pools, execute trades or settle funds.

**Engineering inference:** reuse the pure library as a dependency of a **separate, isolated Stylus wrapper**, rather than treating the current `.rlib`, JSON-lines binary or plain WASM cross-compile as a deployable program. Reuse of the existing checked core is plausible, not yet demonstrated in an SDK-linked, activatable WASM artifact. Keep the host adapter outside the contract; its filesystem, CLI and line-oriented JSON interface are inappropriate onchain. The core's `no_std`/`alloc` design is compatible in principle, but allocation, panic/abort behavior, imports, ABI and runtime limits must be checked in the combined final artifact. The crate-level unsafe prohibition does not audit dependencies.

## 3. SDK, WASM and deployment requirements

**Confirmed by official sources:** The [SDK overview](https://docs.arbitrum.io/stylus/reference/overview) and [quickstart](https://docs.arbitrum.io/stylus/quickstart) specify Rust 1.91.0 or later and `wasm32-unknown-unknown`. The overview describes v0.10.7; the official [latest SDK release checked](https://github.com/OffchainLabs/stylus-sdk-rs/releases/tag/v0.10.10) is v0.10.10 (October 2, 2026). Its [pinned toolchain](https://github.com/OffchainLabs/stylus-sdk-rs/blob/v0.10.10/rust-toolchain.toml) uses Rust 1.91.0; its [workspace manifest](https://github.com/OffchainLabs/stylus-sdk-rs/blob/v0.10.10/Cargo.toml) uses Alloy primitives 1.5.7. This suggests dependency compatibility, but the combined dependency resolution, features, advisories and type identity still require a locked test; do not silently upgrade the core.

For the standard SDK route, the [project structure guide](https://docs.arbitrum.io/stylus/fundamentals/project-structure) describes a root `#[entrypoint]` storage type, `#[public]` methods, ABI-export support and `Stylus.toml`; the official [v0.10.10 example](https://github.com/OffchainLabs/stylus-sdk-rs/tree/v0.10.10/examples/first_app) builds `lib` and `cdylib`. A wrapper can expose a view-style method without persisting route data, subject to SDK/ABI validation. Low-level custom entrypoints exist, but are not needed to justify this recommendation. Pin compatible SDK, CLI, Rust, target, build flags and lockfile for reproducibility.

The [check/deploy guide](https://docs.arbitrum.io/stylus/cli-tools/check-and-deploy) describes `cargo stylus check`: compile, process/compress WASM, validate required `user_entrypoint`, permitted imports, memory and size, and simulate activation with `eth_call`. The quickstart requires Docker for the described check workflow; endpoint support for required state overrides and tool-version behavior should be verified. No check was run here: there is no wrapper artifact and this environment's shell has no Rust/Cargo toolchain. A successful cross-compilation or dry run is **not** current permission to activate.

**Deployment, if separately approved later:** processed WASM is deployed onchain and activation registers the code with [ArbWasm](https://docs.arbitrum.io/stylus/concepts/activation) at `0x0000000000000000000000000000000000000071`. The usual CLI can orchestrate deployment and activation, which are distinct transactions; the general guide's permissionless description is overridden by current chain-specific restrictions. A funded account and transaction fees are required for actual operations, plus any then-applicable review/signature. The [ArbOS 61 release notes](https://docs.arbitrum.io/run-a-node/arbos-releases/arbos61) describe up to 96 KB compressed deployed code via fragments on One/Nova and removal of multi-value WASM support; also check the target's actual decompressed `MaxWasmSize`, import/export, stack and memory constraints. These are protocol/configuration limits, not proof this future artifact fits.

## 4. Proposed integration and trust boundary — engineering inference

1. **ABI and input:** design a versioned Solidity-compatible ABI taking bounded request/candidate structs or tuples; define asset identifiers, bytes32 IDs, `uint128` quantities, `uint16` bps and `uint64` times explicitly. Validate widths and array/string/calldata size before expensive allocation where feasible; retain 1–64 candidates, core validation order, overflow handling, expiry and deterministic route-ID ordering. Choose an explicit schema version and reject unsupported fields/modes. ABI decode/type mappings and empty-storage/view semantics must be tested with the chosen SDK, not assumed.
2. **Evaluate and return:** convert decoded values losslessly to the existing Rust request, invoke `optimize_v1`, and map selected route, quantities, expiry, snapshot, evaluated count and ordered rejections to ABI-compatible bounded results; map structural errors to explicit typed errors/reverts and `NO_ROUTE` to a distinct result. Document any difference from the JSON schema. Test ABI round trips and differential parity against the existing reference for success, error, boundary and permutation fixtures; establish input, output, memory, gas and denial-of-service budgets experimentally.
3. **Freshness and authenticity:** a self-consistent `snapshotId`, supplied expiry, capacity or rational rate does **not** establish truth, source, freshness or available liquidity. For an illustrative synthetic-only view, label the output untrusted and do not use it to authorize funds. Before any real use, choose and independently review a trusted source policy: e.g., verify approved feed/oracle state or signatures over all relevant route and snapshot fields, chain ID, contract address, schema, timestamps, expiry and replay domain; define signer rotation/revocation, expiry and what happens on compromised data. These are design options, not capabilities already present.
4. **Time and replay:** for an onchain freshness policy use the execution environment's block timestamp with an explicit maximum age, future-time tolerance and expiry rules; block time has sequencer/consensus limits and is not an external wall-clock guarantee. A caller-controlled `asOf` alone is insufficient. A stateless `eth_call` cannot consume a nonce or prevent repeated use; actual replay prevention requires an appropriately scoped stateful consumer/nonce mechanism and a separately reviewed transaction design. Revalidate at any later state-changing action because an earlier quote can become stale.
5. **Limits and security:** live pool liquidity changes, MEV, stale block state, reorgs, trusted signers, asset decimals and downstream execution are separate problems. No calculation establishes settlement or guarantees price. Reentrancy and external calls are avoidable in a pure evaluator; any later stateful/external-call integration needs independent threat modeling, security review and controls.

## 6. Recommended next step and deployment checklist

**Next step, only with separate implementation authorization:** design a small synthetic-only, stateless SDK wrapper in a separate crate around the unchanged core. First pin SDK/toolchain and define bounded ABI/errors; locally run SDK TestVM/ABI and differential tests, reproducibly build a Stylus artifact and assess size, imports, memory and resource use. Continue wallet-free, read-only network/policy investigation in parallel. Do not integrate real liquidity or application flows as part of this step. No implementation is started by this audit.

**Before any future deployment or activation, all of the following remain gates:**

- [ ] Obtain explicit user approval for that specific network and operation; recheck current official pause and applicable chain policy.
- [ ] Verify chain ID, recent block/hash, live ArbWasm version/activation gas and limits via a suitable read-only RPC; record evidence and independently corroborate.
- [ ] Establish Sepolia/One/Nova-specific governance execution, installed activation mechanism, codehashes, admin/signers, eligibility, terms, audit and signature requirements; do not assume proposal passage or Sepolia permission.
- [ ] Pin source, lockfile, SDK/CLI/toolchain and build settings; produce and independently verify the exact contract artifact/codehash, ABI and reproducible build. If fragmented, verify each live fragment's code before any root signature, and resolve the audit finding.
- [ ] Pass local unit/property/differential and SDK tests, boundary/invalid-input and ABI tests; perform read-only target-specific `cargo stylus check` where supported; document gas/memory/size results and limitations. A dry run is not authorization.
- [ ] Establish trusted data provenance, freshness/replay design, asset metadata, threat model, downstream execution boundaries, independent application-security review and operational monitoring/expiry/upgrade plan.
- [ ] If and only if later authorized, establish separately the funded-account and fee requirements, activation signature/review and operational readiness; no credentials, signatures, deployment or payments are part of this phase.

**Final decision: CONDITIONAL** — proceed only with a separately authorized offline wrapper design and verification; public-network activation remains blocked or unverified as detailed above.
